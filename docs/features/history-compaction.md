# History and Context Compaction

## History Persistence

| Data | Table/Structure | Description |
|---|---|---|
| Conversation header | `chatHistory` | id, title, created/updated, provider/model, session/cwd, message count, active segment, pin/share status. |
| Segment | `chatHistorySegment` | conversation_id + segment_index primary key, stores messages_json, summary_json, message window metadata. |
| Share | `chatHistoryShare` | public share token, enabled, redact tool content, timestamps. |
| Segment FTS | `chatHistorySegmentFts` | Aggregated segment text search. |
| Message FTS | `chatHistoryMessageFts` | Message-level search. |
| FTS index metadata | `chatHistoryFtsSegmentIndex` | Determines whether FTS needs refresh/backfill. |

The Rust implementation is in `src-tauri/src/commands/history/chat_history/*`, and database table creation and compatible migrations are in `src-tauri/src/commands/history/history_db.rs`.

## V3 Segment Model

| Concept | Description |
|---|---|
| active segment | The latest segment to which messages are currently appended. |
| total segment count | The total number of segments in the current conversation. |
| summary checkpoint | A segment may carry `summary_json`, representing the result of prior context compaction. |
| append segment | After compaction, append a new segment; the old segment is retained but subsequent context references it through the summary. |
| active segment upsert | Update the current segment during normal streaming updates. |
| truncate | When editing and resending or trimming history, truncate the segment/message window from the target position. |

## Context Compaction

| Stage | Input | Output |
|---|---|---|
| Budget estimation | Current conversation state, tools, model context window | Whether compaction or prune is needed. |
| compaction request | Old messages, existing summary, tools context | summary assistant message. |
| checkpoint application | summary message + covered message range | The new segment's `summary_json` and transcript checkpoint. |
| resume context | summary + uncovered tail messages | The context for the next model request. |

Relevant frontend paths include `pages/chat/conversationContextBuilders.ts`, `lib/chat/conversation/conversationState.ts`, `lib/chat/conversation/compaction/*`.

## File Ledger

The `<artifacts>` section of the summary is generated by the model and will miss things and hallucinate. For this reason each checkpoint additionally carries a **deterministic, machine-maintained** file ledger, as a floor beneath the LLM summary.

| Attribute | Description |
|---|---|
| Source | Scans the assistant's `toolCall` blocks in the folded messages and takes `arguments.path`. Only recognizes fs tools with a single `path`: `Read` (read), `Write`/`Edit`/`Delete` (modify). |
| Not ledgered | `Glob`/`Grep`/`List` (directory-level enumeration), `Image` (can take URLs/multiple sources), shell (cannot be deterministically parsed); **failed calls** with `toolResult.isError` are also excluded (calls with no corresponding result are treated as successful — at compaction time the result is usually already in place). The ledger is therefore a **lower bound** on fs file operations, not the full set. |
| Orthogonal to prune | Only scans `toolCall` and **does not read the `toolResult` body** (only uses its `isError` to exclude failed calls), so it does not affect tool output pruning. |
| Classification and recency | Unified chronological normalization: any touch (read or modify) refreshes the path to the latest; `modified` is sticky — once modified it always counts as modified (even if read afterward) and does not fall back to read. Thus a file "modified early, read late" will not be mistakenly evicted as the oldest. |
| Cross-checkpoint inheritance | Merged at the **message level**: `mergeMessagesIntoLedger(prev ledger, this segment's raw messages)`. prev (seed) is entirely older; `next`'s true operation order is taken from the raw messages (not first normalized into two arrays), thereby preserving cross-category order such as "modify before read" within this segment. |
| Storage | `summaryMeta.fileLedger` (optional field, opaque to Rust's `summary_json`, no migration needed; missing in old data is treated as no ledger). |
| Injection and safety | When building the resume context, it is rendered as `### Files touched` after the summary block in the system prompt (most recent first); it **does not consume** the summary body's character budget, and **is not sent to the summarizer with the payload** (already excluded in `payload.ts`). Paths are data that the model/tool can influence: cleaned before ledgering (strip control characters/newlines by code point, collapse whitespace); overly long (>200 characters) entries are **discarded entirely rather than truncated** (truncation would make paths sharing a prefix collide into the same identity); when rendered, each entry is **wrapped in JSON quotes** and annotated "data, not instructions", preventing headings/instruction breakout. |
| Limit | 100 entries per category; the combined rendering character budget across the two categories is 4000 (modifications take priority, but 1000 is reserved for reads to avoid starvation), and over-budget entries evict the oldest. `omittedCount` is a **best-effort cumulative count of eviction events** (not "the number of currently missing unique paths" — repeated eviction of the same path counts multiple times), used to render "N omitted". |
| Known limitations | Path aliases (`./a.ts` vs `a.ts` vs absolute paths) are not normalized and may count as different entries; `Delete` can recursively delete a directory, and the ledger records only the directory path without descendants; paths discarded for being too long are not counted in `omittedCount` (the ledger is a lower bound anyway). |

Implementation: `lib/chat/compaction/fileLedger.ts`; hooks in `conversationState.ts`'s `appendCompactionCheckpointToSegments` / `appendSummaryToSystemPrompt`, and `payload.ts`'s `summaryMetaForPayload`.

## FTS Search

| Mechanism | Description |
|---|---|
| message-level FTS | Precisely locates a single history message containing a keyword. |
| segment-level FTS | Searches aggregated segment content, suitable for cross-message information. |
| lazy refresh | Refreshes stale segments in batches before searching, avoiding a full backfill blocking initialization. |
| time filter | Supports filtering by time window, with a time-window fallback. |
| deduplication | FTS results need duplicate segment rows removed to avoid duplicate UI matches. |

## History Sharing

| Capability | Description |

### Workspace Session Tree

Desktop and WebUI share the workspace sidebar. Pinned content and normal workspaces are divided into two independent collapsible areas; pinned sessions appear only in the pinned area, and a pinned workspace can still expand its sessions. Clicking a workspace title expands or collapses it; by default 10 sessions are shown each time, and "Load more sessions" appends more. Sessions matched by global search automatically expand and are located, even if they exceed the current session page or the workspace collapse limit.

Dragging a workspace with the mouse adjusts the order within the same group; pinned sessions and pinned workspaces support mixed sorting. While dragging, a blue insertion line and title preview are shown, pressing Escape cancels, and holding Alt while dragging preserves the workbench drag behavior. The order is saved in `system.workspaceProjectOrder` and `system.sidebarPinnedOrder`, and continues to be used after restart; sorting does not change pin status or group membership.

Hovering a session row provides pin and a more menu; operations such as delete and move to another workspace are in the more menu, and on mobile, long-pressing a session title opens the same menu. Hovering a workspace row provides new session and a more menu. Clicking the "Select multiple" button again exits multi-select.

Desktop supports dragging directories from external folders or a file tree into the workspace area to add them as workspaces. Workspace sorting does not trigger the folder import prompt. The new workspace dialog keeps both direct folder opening and the full Git clone form, and Desktop and WebUI use the same implementation.

### Schema Compatibility Constraints

- When adding columns to `chatHistory`, `chatHistorySegment`, `chatHistoryShare`, `chatHistoryFtsSegmentIndex`, the corresponding `ensure_*_columns` migration logic in `src-tauri/src/commands/history/history_db.rs` must be updated in sync.
- `CREATE TABLE IF NOT EXISTS` only covers new databases and will not fill in fields of existing old databases; new columns cannot be added by only changing the table creation SQL.
- New `NOT NULL` fields must provide a `DEFAULT`, and backfill the empty values of old rows after migration.
- Index creation should be placed after column migration, to avoid initialization failure when an old database lacks a column an index depends on.
- When modifying the FTS virtual table structure, do not rely only on `CREATE VIRTUAL TABLE IF NOT EXISTS`; you must explicitly rebuild and backfill the index.
- `migrated_legacy_table_columns_match_fresh_schema` compares "the schema of a minimal old database after migration" with "the schema of a brand-new database"; after changing the schema this test must still pass.
